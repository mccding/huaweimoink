## [R1.5.8] 2026-10-07 —— 换日那一拍：刷完就睡，不再开热点等到下一拍

> **一句话**：R1.5.7② 那条「醒得太早就立刻回睡」的护栏，在日历换日这一拍上**永远进不去** ——
> 因为补刷是异步的。`calendar_boot_catchup()` 把帧投进队列就返回，天号当场记进 NVS，屏却还没刷；
> `frame_task` 又要到 `app_main` 末尾才创建，于是护栏 ③ `frame_pending_display()` 不许带着未上屏的
> 一帧睡下去，那一拍只能落回正常启动、开热点、把整段 `sleep_s` 烧完。
>
> 实测这一拍 **196 秒 → 16.4 秒**（同一台设备、同一套无扰动观察，见下）。

### 修复

- **定时自醒路径上的日历补刷改成「当场刷完」**：新增闸门 `calendar_display_sync(on)`
  （`src/calendar.c/h`）。`main.c` 在起 SNTP 之前 `calendar_display_sync(auto_wake)` 拉起闸门，
  `xTaskCreate(frame_task, …)` 之前落下。同步 flush 走 `render_once(async=0)`，**不投 `s_frame_ready`
  信号量** → `frame_pending_display()` 恒为 0 → 早睡护栏四条全部成立 → 刷完直接 `power_enter_deep_sleep()`。
- **为什么是闸门而不是给 `catchup_today()` 加实参**：定时自醒那一段里补刷有**三个入口** ——
  `calendar_boot_catchup()`、`calendar_sntp_run()` 内部那次补刷、以及更早的 `calendar_display_sync`
  之前的调用点 —— 它们都发生在 `frame_task` 存在之前。逐个传实参容易漏一个，漏掉的那个就把整条
  优化抵消掉；共用一个状态则不会。
- **按键 / 上电开机不开这道闸**：那条路要早点起热点等人传图，不该为一次刷屏多挂 15~25 秒；
  页面推日期（`/api/time` POST）也保持异步，免得 HTTP 应答被四色全刷挂住。

### 实测（两台都装本版，2026-10-07）

- **换日那一拍醒着多久**（MoInk-0D10，USB-Serial-JTAG 节点边沿，期间**零 HTTP 请求** = 无观察者污染）：
  - 刷后 R1.5.8：`09:16:30.561 ATTACH` → `E (16408) main: woke early, nothing due for 86384s, back to sleep`
    → `09:16:46.972 DETACH 本次醒着 16.4 秒`。
  - 刷前 R1.5.7 的同一拍（本版立项依据，R1.5.7 验收 L5，同一台同样无扰动取数）：
    **11:09:07 RTC 叫醒 → 11:12:23 才回睡 = 196 秒**。
  - `86384 s` 这一行本身就是换日成功的旁证：86400 − 16 = 86384，说明打这行日志时设备自己的墙上时间
    已经在 00:01 之后，而下一次到期还要再等一整天 —— 天号在本次开机内就消费掉了。
- **日历没被修坏**（假钟 7 分钟换日法：把日期推到 23:54，让它在大白天走一次换日）：
  - 0D10：`shown_day` 20733 → **20734**，回读自报 `2026-10-08 00:29:46`，`next_in_s=84614`（正常等下一日）。
  - MoInk-2DEC（**日历主机**：`cal_on=1 / tod_s=60 / style=1 / lang=zh / tz_min=480`）：`shown_day` 同样推进到
    **20734**。固件的规则是「只有真正上屏成功才记天号」（R1.5.3②），所以这条读数等于「8 号日历确实刷上了屏」。
  - R1.5.7② 那条早睡护栏**第一次被正面触发**（L6 测轮播时 `woke early` 计数 0/7，那次是零触发）。
- **两台都未观测到的（不写成结论）**：2DEC 没连 USB，唯一观察通道是局域网 ping，而 ping 只盯得住一个 IP
  —— 若那一拍之后设备复位并换址，这条通道看不见它的清醒窗口。所以 2DEC 只记「换日成功」，
  「那一拍射频有没有起」不记为实测。
- **一条待查、与本版无关的读数**：2DEC 那次按键开机读到 `synced=0 / t=0 / next_in_s=3600`，即墙上时间回了
  1970，R1.5.3③ 的「没校上就 1→2→4→8→12 小时退避自醒」正在工作。同一台 0D10 走同样的路时墙上时间跨睡眠
  保住了（回读 2026-10-08 00:29:46）。本版一行都没碰时钟与电源路径，此读数记为待查，不当成本版的回归。

## [R1.5.7] 2026-10-07 —— 定时自醒的两个「不该醒着」：换完图即睡 + 醒太早即回睡

> **这一版分两刀，① 已实机验证，② 是 ① 装到设备上之后测出来的另一半。**
>
> R1.5.6 让周期跟上 `int_s` 了，但实机读数同时暴露出第二半问题：**节奏对了，电还是要被抽干**。
> 300 秒一个周期里设备醒着 **257 秒**（节点日志：12:17:41 AWAKE → 12:21:58 ASLEEP），
> 而文档与代码注释到处写的都是「醒来上屏后立刻回深睡」——那句在清醒路径上从来没成立过。
>
> 现场读数（设备自己的接口，不是推断）：
> - `12:23:27  uptime=61  cur=4  next_in_s=257  int_s=300` ⇒ 这一拍的实际消费时刻 = 12:22:44 = **开机后第 18 秒**；
> - boot 分支（`main.c` 的 `auto_wake` 块）在 `uptime ≈ 3 s` 就判完到期与否了，而
>   `idle_monitor_task` 要等 `netif_ap_init()` + `captive_dns_start()` + httpd 起完才第一次跑到
>   （任务创建在 `main.c` 末尾，实测约 `uptime 15~20 s`）；
> - 于是一拍常常是「boot 分支判断时还没到期 → 落回正常启动 → 起热点 → 十几秒后成熟 → 由
>   `carousel_awake_tick()` 换图 → 然后把整段等人窗口烧完」。
> - **诚实标注：那 ~18 秒的相位差本身没定性**。mono 的记账是 `el_醒来 = el_睡前 + arm`，
>   按 `power.c:47` 的补账写法应当恒等于 `int_s`，即 boot 分支本该每次都命中 ——
>   实测它没有，说明补账或到期判定里还有一处与代码读出来的不一致。先不写进结论，
>   留给本版实测（三条周期连测看相位是否逐拍累积）再定。上一条会话里我把它归因成
>   「内部 RC 让定时器早醒 19 秒」，那个解释在 mono 算术下站不住，**撤回**。

### ① 实机复核（2026-10-07，MoInk-0D10 / R1.5.7 ①，`int_s=300`、`sleep_s=180`、`wake_s=0`、日历关）

结论：**换完即睡这条成立；但占空比远没回到当初估的 15 %，因为还有另一半问题 —— 醒得太早。**
下面全部是设备自己报的数（`/api/time` 的 `mono`/`up`、`/api/carousel/list` 的 `cur`/`next_in_s`）
+ 一次性的 ICMP 边沿，观察手段本身只在清醒窗口里发请求（每个请求都会 `power_activity()`，
密集轮询会把静默门槛一直顶住 —— 这一条已经踩过，见下）。

- **① 有效，且是「静默 15 秒」这条在起作用**：`1791312808  up=323  next_in_s=123`（那一拍还差
  **123 秒**才成熟），停止一切请求后 `1791312826` 设备即不可达 —— **静默 18 秒就睡了**，没有把
  180 秒空闲窗口烧完。
- **周期是准的**：两次换图的消费时刻 `1791312632`（`next_in_s` 从 2 跳到 299 的那一刻）与
  `1791313225`（`up=109` 且 `next_in_s=282` ⇒ 消费于 `up=18`）之间跨 **2 拍 = 593 秒** ⇒
  **平均 296.5 秒/拍**，对 `int_s=300` 差 1.2 %。同一段里 `mono` 走 439 而墙钟走 435 ⇒
  设备单调钟与墙钟 1 % 内一致，所以这个周期数不是记账假象。
  （R1.5.6 那句「周期被钉在 256~266 秒、与 `int_s` 无关」到此正式解决。）
- **当时判为「剩下的一半：定时自醒普遍醒得太早」，这条解释已被撤回**（见下「② 实机复核」）。当时每次「醒来后
  第一次可达」抓到的 `next_in_s` = **158 / 185 / 11**，前两次读成「醒过来时这一拍还差 150~190 秒」。
  用串口 10 ms 采样重测后，剩余量只有 **15 / 30 / 45 秒**（按 `SWAP_QUIET_S` 一格 15 秒），而那三次读数取自我
  每 5 秒 `curl` 的现场 —— 是我把那一拍的换图推迟了，不是设备醒得太早。**150~190 秒这个量级不可复现。**
  同理，本条目先前写的「每周期醒 100~205 秒、占空比 33~68 %」也只能当上界读（同一污染源），
  「降到约 45~55 秒」则是没测过的估算，两处一并作废；实测每拍醒 **约 40 秒 / 占空比 14.3 %**。
- **「为什么早醒」这个问题本身随上面的撤回消失，不要再回去找它的根因**。留在记录里的是当初那个否证：
  上面 `mono` 与墙钟 1 % 一致，真有小 200 秒量级的时钟误差，记账一定会露馅 —— 后来确实露馅了，
  露的是我的观测方式。② 的实际定位因此改成「相位差 >60 秒时的保险」，见下条。

### ② 实机复核（2026-10-07，0D10 测占空比 / 2DEC 测日历回归）

观测手段换了，**这一轮全程不主动发 HTTP**：好用的数据线还给 0D10，用采集器以 10 ms 紧跟
`/dev/cu.usbmodem*` 的枚举（先做过对照实验：pyserial 以 `dtr=True rts=True` 打开节点**不复位**
设备 —— `uptime 197 → 199`，正好等于真实经过的 2 秒），边沿再与 ICMP 对齐。于是「醒着的秒数」
第一次是不含观察者污染的读数。

- **① 的占空比改善是实测的**（0D10，`int_s=300`、`sleep_s=180`、`wake_s=0`、日历关，11:35–11:56）：

  | 醒 onset（宿主机 epoch） | 醒着 | WiFi 起过吗 | 这一跳做了什么 |

  「①-only 每周期醒 100~205 秒」都取自我每 5~20 秒 `curl` 一轮的现场，那两段里 180 秒空闲窗口

  停止一切请求后 **18 秒**设备即不可达，而那一拍还差 123 秒才成熟。

  `main.c:545`，② 的判断在 `main.c:613`，**在它的下游** —— 早的那行既然每跳都收得到，
  晚的那行没出现就是真没发生。原因是 ② 的第 ⑤ 道门槛：`power_next_wake_s()` 取三条节奏的
  最小值，而实测剩余量按 **+15 秒一格**（恰好 `SWAP_QUIET_S`）长到 45 秒就被清醒路径换图消费掉

- **上一段那句「醒过来时这一拍还差 150~190 秒」按观察者污染撤回**：那三个读数

  逐秒吻合）、`sntp_at` 恒为 3 且 `mono < 43200` ⇒ SNTP 没有半路把假钟纠回真值。**② 没修坏日历。**
- **L5 的机制注记（要写下来，否则下次会被当成 ② 生效）**：这一次换日由 `calendar_boot_catchup()`
  的**异步**补刷画掉。它在 `main.c:568` 就跑在 boot 分支之前，`calendar_show(1)` 入队的**同时**就
  记了 `s_shown_day`，于是 `main.c:578` 的 `calendar_next_in_s() == 1` 不再成立（`ticked=false`），

  换日摊得上一个带射频的 3 分钟窗口 —— 与 ① 修掉的是同一类开销，只是频率一天一次。

### 新增
- **`frame_pending_display()`**（`src/frame.c` + `frame.h`）：有没有「已排队但还没上屏」的画面。
  异步入口（日历补刷 `calendar_show(1)`、`frame_queue_slot()`）只把缓冲交给显示任务，
  真正刷屏由 `frame_task` 做 —— 而 `frame_task` 要到 `app_main` 末尾才创建，所以开机早期
  **带着没上屏的一帧睡下去 = 这一天的日历永远不再重试**（`s_shown_day` 当场就记进 NVS 了）。
  这是 ② 唯一的日历侧护栏。
- **`BOOT_IDLE_S`（60 秒）**：早醒回睡的剩余时间门槛（见下）。
- **`carousel_awake_tick()` 回报换图结果**（`bool`，`true` = 本次真换了一张且刷完）：
  `frame_show_slot()` 是同步的（拿 `s_fb_mutex` → `epd_display_2bpp_wh()` → 自己调
  `epd_panel_deep_sleep()`），返回时面板已定版，调用方立刻入睡不会刷到一半断电。
- **`power_idle_s()`**（`src/power.c` + `power.h`）：只读 accessor，算 `s_last_activity`
  距今几秒。**本版 power.c 只加这一个函数**，`power_should_sleep()` / 武装口径 / `MIN_ARM_S`
  一行未动。

### 修改
- **① `idle_monitor_task`（`src/main.c`）换完图即回睡**：清醒路径换图成功后，不再等
  `sleep_s` / `AUTO_WAKE_WINDOW_S` 烧满，四条护栏同时满足才睡 ——
  ① `power_auto_wake()`：本次确为定时自醒（按键 / 上电开机是要等人传图的，窗口必须留满）；
  ② `power_hotspot_in_s() != 1`：热点节奏没到期（与 boot 分支**同一条**护栏，不新发明语义）；
  ③ `netif_ap_client_count() == 0`：没人连着热点；
  ④ `power_idle_s() >= SWAP_QUIET_S(15)`：请求静默够久。第 ④ 条是给传图 / OTA 让路的：
  上传是一段一段 call `power_activity()` 的，静默才说明这条连接真停了，否则会把写入拦腰截断
  （截断不会 brick，新镜像不被确认就退回旧版，但白等一次）。
- **② boot 分支：这一拍还差得远就立刻回睡（`src/main.c`）**。原来 `auto_wake` 块里只有「做到期的那件事
  → 睡」一条路，判定为「还没到期」就整段落回正常启动，于是设备醒着干等下一拍（当时按「普遍差 150~190 秒」
  立项，实测剩余量只有 15 / 30 / 45 秒，见上「② 实机复核」⇒ 这条在 `int_s=300` 下从未获得触发资格）。
  现在补第二条睡路，五条同时满足才睡：
  ① `!ticked` —— 这次醒来确实没做成到期那件事；
  ② `!failed` —— **「到期但做失败」必须落回正常启动、把热点窗口留出来**，让人来救。轮播失败也会
     照旧消费掉一拍（退避），`next_in_s` 一下跳回 `int_s`，不挡这条就等于静默失败到永远；
  ③ `power_hotspot_in_s() != 1` —— 热点同时到期就照常起热点等人；
  ④ `!frame_pending_display()` —— 有画面排着还没上屏就不睡（日历补刷那条异步路，见「新增」）；
  ⑤ `power_next_wake_s() > BOOT_IDLE_S(60)` —— 剩余不到 1 分钟不值得再醒睡一次。
  睡路复用 `power_enter_deep_sleep()`，因此 `MIN_ARM_S` 兜底、`ota_web_confirm_flush()`、STA 挂起、
  以及 `mono` 记账口径全部与既有一致，**没有新增第二条武装逻辑**；且**必须**排在
  `power_mark_hotspot_wake()` 之前返回 —— 那句会把热点节奏起点挪到此刻，每次早醒都重置一次的话
  热点就永远不会到期。
  只在 TIMER 自醒路径判（按键 / 上电开机的窗口不受影响）。早醒时串口会出一行
  `woke early, nothing due for Ns`（用 ERROR 级是故意的：本工程 `CONFIG_LOG_MAXIMUM_LEVEL=1`，
  INFO/WARN 全被编译掉，这是「一个间隔里跳了几次早醒」唯一到得了串口的证据）。
- **页面**：轮播卡新增一条明示 ——「换完图后设备约 15 秒内就回深睡，别把本页一直开着等它换图；
  连不上就按机身按键或重新上电唤醒」。
- 文档口径统一：`docs/CONTRACT.md`、`docs/入门教程.md` 里「到点自醒上屏后立刻回深睡」补成
  「boot 分支与清醒兜底两条路径都换完即睡（R1.5.7①）」，并把「换图期间热点会短暂开启」写明。

### 已知代价
- 走局域网 STA 浏览控制页时 `netif_ap_client_count()` 看不见这个浏览器（它连的是路由不是热点），
  所以只看「静默 15 秒」：页面开着但 15 秒内不点击，换完图就可能睡下去，下一次点击连不上，
  按键唤醒即可。这与 boot 分支「换完即睡」一直是同一语义，本版只是让清醒路径也照做。
- 每拍仍要多醒 `SWAP_QUIET_S` 这 15 秒 + 刷屏 15~25 秒（四色全刷的物理时间，省不掉）。
- 本条原文写的「② 之后每跳醒 3~5 秒」「一个周期醒着降到约 60~90 秒」**两处都是没测过的估算，
  按实测作废**（见上「② 实机复核」）：一次开机光走到 `ota_web_confirm()` 就要 **12.096 秒**
  （六次读数一致，是固定的面板上电延时链），所以任何一跳的清醒下限就是 ~13 秒，"3~5 秒"不可能；
  而 `int_s=300` 实测每拍醒 **16.3 / 31.4 / 46.4 / 61.4 秒**、平均 **约 40 秒/拍（占空比 14.3 %）**，
  这个改善来自 ①，② 在实测的剩余量（≤45 秒）下从未获得触发资格。
- **观察手段的坑（已踩过，写下来免得下次再当成设备行为）**：`power_activity()` 有 28 处调用点，
  **每一个 HTTP 请求都会把静默门槛顶回去**。用 3 秒一次的密集轮询测「换完即睡」一定测不到它睡，
  只能测出「请求一停 18 秒后就睡」。要测清醒时长只能一个清醒窗口取一次读数，边沿靠 ICMP；
  而 ICMP 也不能判「睡了」——刷屏那 15~25 秒里 STA 自己会掉，`DOWN` 有两种含义。

## [R1.5.6] 2026-10-06 —— 轮播按设置的间隔换图了（补「醒着也要换图」入口 + 间隔下限 5 分钟）

> 用户口径：**「不管我设置 1 分钟还是 10 分钟，都是 10 分钟刷新，这显然不正」**。
> 18 分钟不插手实测（判据：C3 深睡会关掉 USB-Serial-JTAG，`/dev/cu.usbmodem21101` 消失 = 真睡着，
> 重新出现 = 醒着）抓到的是严格重复的节奏 **`醒 180 → 睡 30 → 醒 16 → 睡 30`**，单元约 **256~266 秒**；
> 同期 `cur` 在 1080 秒里只走了 3 张（≈ 360 秒 / 张，而配置是 60 秒）。也就是说周期由
> `AUTO_WAKE_WINDOW_S(180)` 与 `MIN_ARM_S(30)` 两个常量决定，**与 `int_s` 无关**。
>
> 链条（`power.c` / `carousel.c` / `main.c` 逐行核对，不是猜）：
> 1. `carousel_next_in_s()` 用返回值 `1` 表示「已到期」，这个 `1` 也进了 `power_next_wake_s()` 的取最小；
> 2. 入睡时 `arm_s < MIN_ARM_S` 被抬成 **30 秒**（power.c:157）；
> 3. 30 秒后醒来，`el ≈ 30 + 开机耗时 < int_s` → 判定**还没到期** → main.c 的 `auto_wake` 干活动作整块跳过；
> 4. 于是落回正常启动，把 180 秒空闲窗口**整段烧掉**——这段时间倒计时成熟了，可轮播**没有任何醒着的入口**
>    去消费它（日历有 `calendar_awake_tick()`，轮播只有开机那一次 `carousel_boot_tick()`）；
> 5. 窗口到点入睡 → 回到第 1 步，如此往复。
>
> 曾经的头号嫌疑「每次入睡都崩溃重启」**已证伪并撤回**：实机 ota_0 / ota_1 的应用头与
> `flash_kit/moink_R1.5.5_app.bin` 同构（sha `5ab7972c…`），该构建的 `wifi_event_handler` 反汇编里

## [R1.5.5] 2026-10-06 —— 接通「断电重上电自动回日历」的真判据 + 治日历卡片的假阴性

> 现象是用户报的：「设备重新上电后并没有自动刷写日历」，而日历开关是开的、R1.5.3 号称已经修过这件事。
> 临时把日志提到 INFO 编了一版诊断固件抓开机现场，抓到的不是「没修好」而是**「从来没生效过」**：
>
> ```c
> calendar_boot_catchup(wake == 0);          /* R1.5.3① —— 恒假 */
> ```
>
> IDF `components/esp_hw_support/sleep_modes.c` 对**不是从深睡醒来**的复位（上电、EN 硬复位、OTA 重启）
> 返回的是 `wakeup_cause |= BIT(ESP_SLEEP_WAKEUP_UNDEFINED)`；而 `ESP_SLEEP_WAKEUP_UNDEFINED` 是**枚举 0**，
> 所以 `BIT(0) == 1` —— 位图**永远不等于 0**。于是 `catchup_today(force=0)` 撞上
> `if (!force && s_shown_day == today) return;`，只要 NVS 的 `cal_day` 记着今天，同一天内断电重上电就再也不回屏。
> 换日 00:01 那条定时自醒路径不受影响（它直接走 `calendar_boot_tick()` → `calendar_show(0)`）。

### 修复
- **固件 `src/main.c`**：强制回屏的判据改为「本次复位不是从深睡醒的」=
  `calendar_boot_catchup((wake & (1u << ESP_SLEEP_WAKEUP_UNDEFINED)) != 0)`，并把这条陷阱写进代码注释
  （含 IDF 文件与行为），免得下次又有人写 `wake == 0`。
- **控制页日历卡片**：开机进页面时 SNTP 通常还要 4~6 秒才落地，那一刻读到的是中间态，而
  `calendar.c` 回显的 `sntp_at` 是**上次校时的单调时刻**（`RTC_DATA_ATTR`，掉电才归 0）而不是布尔量，
  页面用 `!(sntp_at > 0)` 判「从未校时」就会假阴性地一直挂着
  「自动校时 · 尚未自动校时（下次醒来时补）」。现在开页在 12 秒后**只补读一次**（`calReread` 一次性闸门）。
  刻意不做轮询：每一个请求都会让设备 `power_activity()`，轮询等于把深睡彻底废掉。
- **控制页日历卡片改版**：「校时的原理与边界」这类机制长文（NTP 主机名、12 小时门槛、UDP 123、
  RC 漂移、退避阶梯）不再常驻页面 —— 收进 `<details>` 折叠块，常驻只留一句「开着启用联网时设备自己
  把日期校准，**不必**再手动点同步」，原文一字未删。

## [R1.5.4] 2026-10-06 —— 修「OTA 上去的固件开机 OOM 自杀 → 被静默回滚」+ 让回滚在页面上看得见

> 这一版回答的是「为什么 OTA 明明传成功了，设备却一直是旧版本」。串口抓不到，最终用 esptool
> **只读** dump 分区与 otadata 定案，链条是三段，缺一不可：
> ① R1.5.3 的 `frame_init()` 申请 **120,000 字节**（800×600 画像）时，唯一能服务它的那段连续
> 空闲只剩 **118,784** 字节 → `malloc` 返回 NULL → 同函数里的 `abort()` 在开机 **347 ms** 就把设备打死；
> ② 崩溃循环里根本走不到「自我确认」那一步，bootloader 在第二次启动时给 ota_1 盖上 **ABORTED**，
> 从此**永久跳过**这个槽；③ 于是设备退回 ota_1 之外唯一有效的 ota_0 —— 里面躺着 **R1.5.0**。
> 用户侧看到的就是「升级成功、重启完还是旧版本」，而页面没有任何一处能说出这件事发生过。
> 为什么 R1.5.0 活得下来：它和 R1.5.3 的静态 RAM 只差 **1,296 字节**（`_heap_start`
> 0x3FC9D920 ↔ 0x3FC9DE30），而这一千多字节正好压在 120,000 那条线上 —— 新增 `.bss`（日历字库这类）
> 会 **1:1** 吃掉这块余量，所以「只是加了个模块就起不来」不是玄学。
> 三条修复按「不再自杀 / 不再被静默退回 / 被退回了要看得见」排列。

### 修复
- **① 帧缓冲按当前画像分配，且永远不再 abort**（`frame.c` / `frame_init`）：申请量取
  `epd_profile()->buf_len`（768×552 → **105,984**；800×600 → 120,000，上限 `STORE_FRAME_MAX`）；
  拿不到 800×600 那一档时**退回 105,984 并把 A1 驱动档强制为 seq552**，照样建好互斥量与信号量后
  正常返回 —— 分配失败不再是开机致命错误。运行期容量 `s_fb_len` 成为**每一条写入路径的唯一上限**
  （`frame_display_now` / `frame_recv_locked` / `frame_show_slot` / `render_once` 一律拒绝超限载荷，
  收帧请求体上限同步收为 `FRAME_HDR_LEN + s_fb_len`），缓冲不存在时回 500 "no frame buffer"。
  开机用 ERROR 级打印 `boot stat: fb %u bytes, free heap %u, largest block %u`（本机
  `CONFIG_LOG_DEFAULT_LEVEL_ERROR`，只有这一级到得了 USB 控制台），下次再出这类问题不必拆机。
- **①b 几何闸门与契约对齐**（`epd_frame_geom_ok`）：A0 只认自身画像；A1 的 768×552 **两档都收**
  （日历恒用 768×552）；**800×600 只在 `a1_mode=2`（对照档）被接受，且缓冲必须真有 120,000 字节**
  —— 默认档那块只有 105,984，收下 120,000 字节帧等于把堆写穿。
- **①c 槽位读取按缓冲容量设限**（`store_slot_read(…, cap, …)`）：槽里字节数大于 `cap` 时
  `ESP_LOGE "slot %u holds %lu bytes, buffer only %u"` 并返回 -1，不再越界写。轮播早已跳过不可读槽
  （`carousel.c`），所以模式退回后 NVS 里遗留的 800×600 旧帧会被**转过去**而不是卡死换日。
- **② 自我确认提前 + 每次入睡兜底**（`ota_web.c` / `power.c` / `main.c`）：`OTA_CONFIRM_MS`
  **45000 → 12000**；`ota_web_confirm()` 从"外设任务建完之后"提到 **`frame_init()` 成功后立即起算**。
  新增幂等的 `ota_web_confirm_flush()`，并在 `power_enter_deep_sleep()` 的**第一行**调用 —— 两个入睡点
  （空闲监视、auto_wake 短路）都覆盖。理由：`esp_deep_sleep_start()` 永不返回，**深睡就是一次复位**，
  旧版那个 45 秒窗口 + 日历到点入睡 = 只要当天没等到确认就被静默 stamp ABORTED（本仓库实测过一次）。
- **③ 回滚可见化：`/api/info` 六个新字段 + 页面两处回显**：`ota_web_status()` 用
  `esp_ota_get_state_partition()`（⚠️ IDF 6.1 **没有** `esp_ota_get_state_info` 这个函数）读运行槽与
  备用槽的 `esp_ota_img_states_t`，`/api/info` 新增 `fb` / `heap_max` / `ota_run` / `ota_state` /
  `ota_other` / `ota_other_state`；`a1_mode` 从此回报**生效值**（`epd_get_a1_mode()`）而不是 NVS 存量，
  页面按它选几何就不会跑在缓冲前面；`POST /api/settings` 在缓冲服务不了 800×600 时**拒绝存 `a1_mode=2`**。

## [R1.5.3] 2026-10-06 —— 修「同一天断电重上电，日历再也不回屏」+ 没校上时不许睡死

> 起因是实机反馈：OTA 到 R1.5.2 后故意断电重上电，屏上还挂着待办，日期始终不回。串口抓不到
> 任何东西（C3 深睡时 USB-Serial-JTAG 随内核掉电，节点直接消失），改用 esptool **只读** dump
> NVS 定案：键 `cal_day` = `0x50FC` = **20732 = 正好是 2026-10-06 的 epoch 天号**，即设备认为
> 「今天这块屏已经刷过了」。而 R1.5.1 起这个天号是**跨掉电**存活的（从 RTC 内存搬进 NVS），
> 于是三个补刷入口共用的一道闸门把活全拦掉了。根因与 OTA 成没成功、SNTP 通不通**都无关**：
> 同一天内断电重上电必然复现 —— 这正是「不会变日期的假日历」里最难自己爬出来的那种。

### 修复
- **① 开机那一次不许拿 `cal_day` 否决回屏**（`calendar_boot_catchup(int screen_unknown)`，
  main.c 传 `wake == 0`）：`cal_day` 只回答「今天刷过没有」，回答不了「屏上此刻挂着什么」——
  墨水屏双稳态，掉电 / 复位 / OTA 重启之后旧图（比如手动推上去的待办）还在屏上，而设备无从得知。
  因此**只有从深睡醒来**（定时自醒 / 按键，屏内容原样保留）才允许按天号跳过；其余开机一律强制
  把当天日历回屏一次。按键唤醒仍然不会白刷屏。
- **② 画失败不再烧掉天号**（`calendar_show()`）：原来是「无论成败都记为已处理」，一次偶发的
  EPD busy / 排队失败就把整整一天永久判给「已刷过」，再也没机会补。现在只在 `r == 0` 时才写
  `s_shown_day` + `persist_day()`，失败留给下一次开机 / 补刷入口重试。
  配套加了 `s_try_day`（只在 RAM）：**一次开机最多试一次**，挡掉 `idle_monitor_task` 每秒一次的
  catchup 对着坏屏连刷 —— 这才是原实现烧天号的真正理由。
- **③ 没校上时不许「不带定时器就深睡」**（`calendar_next_in_s()`）：R1.5.2 的口径是「时钟不可信
  → 日历不参与定时（返回 0）」，配上 `wake_s=0` + 轮播关 ⇒ `power_next_wake_s() == 0` ⇒
  `esp_deep_sleep_start()` **一个定时器都不武装**，从此只能靠人手按键。一次网络抖动（路由器重启、
  改了 WiFi 密码、UDP 123 临时被拦）就把设备冻成不可自愈的假日历。现在没校上时返回**指数退避
  窗口：1 h 起、每失败一次翻倍、12 h 封顶**（计数器 `s_ntp_fail` 走 RTC 内存，跨深睡有效、
  掉电后夹到上界防随机值）；只有「STA 根本没配」才继续返回 0 —— 那时醒了也白醒，唯一路径是页面推日期。

### 新增
- 日历状态应答（`GET /api/time`、`/api/calendar/cfg`）追加 **`ntp_try`** = 本次掉电周期内
  连续校时失败次数。它是 ③ 的观测量：`synced:0` 时 `next_in_s` 的含义从「距换日时刻」变成
  「距下次重试校时」，页面据此改口（`约 2 小时后自己再试校时（已连续失败 2 次）`），
  不再谎报成「不会自动改日期」。旧固件无此字段 → 退回 R1.5.2 的说法，不猜。

### 修改
- 页面日历页 hint 追加两句：退避阶梯 1→2→4→8→12 小时；以及「掉电 / 复位 / 升级后那次开机会强制
  回屏一次」的理由 —— 让用户知道屏上留着的是旧图而不是设备罢工。
- `calendar.h` 的模块契约注释同步（`cal_day` 语义、退避、开机判定、`calendar_boot_tick` 成功才记天号）。

### 涉及文件
`src/calendar.c`（①②③ + `ntp_try`）、`src/calendar.h`（签名 + 契约）、`src/main.c`（开机传

### 新增
- **SNTP 自动校时**（日历开着 + 「启用联网」已开才做）：主 `ntp.aliyun.com`，静默 12 秒后试

  ① 正常开机后由后台任务补一次 —— 对应「白天把屏带走、晚上装回来」；

## [R1.5.1] 2026-10-06 —— 修「开了局域网 WiFi 就永远睡不着 → 日历成了假日历」

> 现象：日历开关、换日时刻、日期同步全部正常（`/api/time` 给出 `synced:1 / next_in_s` 正常），
> 屏幕上的日期却永远不变。根因不在日历，在**入睡路径**。

### 修复
- **STA 已连接时每次入睡都 abort**（真凶）：`power_enter_deep_sleep()` 里 `esp_wifi_stop()` 会抛
  `WIFI_EVENT_STA_DISCONNECTED`，回调无条件 `ESP_ERROR_CHECK(esp_wifi_connect())` —— 此时 WiFi 驱动
  已停，调用必失败 → abort → 复位重启 → 空闲 3 分钟后再来一次，**每 3 分钟一个循环**，
  `esp_sleep_enable_timer_wakeup()` 永远走不到，所以定时器从没被武装过。
  现在入睡先立闸门 `netif_sta_suspend_begin()`，断线回调看见闸门就不重连；
  非入睡的正常掉线仍自动重连，且重连失败只打 warning 不再 abort。
- **崩溃/掉电重启把「今天已刷」误记**：已上屏天号原先放 `RTC_DATA_ATTR`，复位即清零 →
  重启后 `anchor_today()` 反过来把当天标成已处理（现场证据：`shown_day:20732 / next_in_s:85614`）。
  天号改落 NVS 键 `cal_day`，跨复位、跨掉电有效。
- **刚保存「自动唤醒」间隔，设备就每 30 秒醒一次**：热点节奏的基准时刻只在开机时刷新，
  本次开机时间隔还是 0 的话，改完非 0 会拿陈旧基准算成「已到期」，被 `MIN_ARM_S` 兜底成 30 秒。
  `settings_set_wake()` 之后补一次 `power_mark_hotspot_wake()`（轮播 `carousel_set_int()` 早就是这么做的）。

### 新增
- 日历改为「只要开着就该有当天」（方案 B）：三个入口共用 `catchup_today()` —— 开机（`frame_init()`
  之后 `calendar_boot_catchup()`）、页面推来日期、换日时刻到点而设备正醒着
  （`idle_monitor_task` 每秒 `calendar_awake_tick()`）。缺哪一天补哪一天，天号已落 NVS，
  所以按键唤醒不会每次重刷同一张日历。开启日历时也会立刻补刷当天（旧行为是故意不抢屏）。
- 日历与轮播互斥这一点不再靠猜：两者抢同一块屏，页面已明示；用户实际用法是二选一。

### 涉及文件
`src/netif_ap.c/.h`（入睡闸门 + 断线不 abort）、`src/power.c`（入睡先立闸门）、
`src/calendar.c/.h`（`cal_day` 落 NVS + `calendar_boot_catchup()` / `calendar_awake_tick()`）、
`src/main.c`（开机补日历 + 醒着换日 + `wake_s` 基准刷新）、`src/version.h`、`page/index.html`（仅版本号 meta）

- `api` 保持 2，分区表不变 → R1.5.0 可直接 **Web OTA** 升上来；NVS 新增键 `cal_day`

- 关闭 STA 的设备在 R1.5.0 上不会有此症状（不入睡或纯 AP 时不触发 abort），日历能正常换日。

  `01:32:04 按键唤醒 → 01:35:35 自己睡 → 01:36:05 无外力自醒 → 01:39:05 睡 → 01:39:35 自醒`，
  修复前同一位置必 abort；`/api/time` 在关闭自动唤醒后给 `shown_day:20732 / next_in_s:80163`
  （= 明天 00:01，与 `86400 - 6297 + 60` 精确相符）。
